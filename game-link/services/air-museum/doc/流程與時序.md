# air-museum 流程與時序

直連架構，協定沿用 `gate.Pack`（packType / svt / method / info）。WebSocket 連線單一 Server。

---

## 裝置與連線 uid（ValidateReq.device）

認證身分**一律**以 **`ValidateReq.device`** 為準；**勿**在 token 使用 `key=`，**勿**在 token 內帶 `device=`。相容舊客戶端主畫面仍可使用 `projector`。

**約定**：單館單線—同一種非 `player` 裝置在整個伺服器進程下同時僅一通連線有效（重複登入會踢舊連線）。

| device 值              | 說明                      | 認證後連線 uid   | player 表列                   |
| ---------------------- | ------------------------- | ---------------- | ----------------------------- |
| `gameScreen`           | 遊戲投影幕（主機）        | **1**            | 種子列（見下）                |
| `projector`            | （相容）等同 `gameScreen` | **1**            | 同 uid=1                      |
| `playerRegisterScreen` | 玩家註冊／玩家螢幕        | **2**            | 種子列                        |
| `airplaneScreen`       | 飛機螢幕                  | **3**            | 種子列                        |
| `playerGameEndScreen`  | 玩家遊玩結束螢幕          | **4**            | 種子列                        |
| `player`               | 玩家手持 app              | **≥5**（SERIAL） | runtime `CreatePlayer` 新增列 |

建表後會 **INSERT** uid **1～4** 之四筆種子列（`name` 以 **`__fixture.`** 為前綴，供 Server 綁線時與 ValidateReq.device 對照驗證）；**請勿手動篡改**這些列的 uid／該占位 name， handheld 不可用 `token uid=1..4`。**真實玩家**僅能由 `device=player` 路徑新增，且 **uid 自 5 起**（SERIAL 於啟動時 `setval` 對齊）。

---

## Postgres：`player` 固定終端種子列

與 **`air_museum.player`** 同表：啟動時 **`INSERT … ON CONFLICT (uid) DO NOTHING`** 寫入 uid 1～4，欄位 `name` 分別為  
`__fixture.gamescreen`、`__fixture.playerregisterscreen`、`__fixture.airplanescreen`、`__fixture.playergameendscreen`（其餘欄位預設值）。

**auth** 時 Server 依 **device** 映射到預期 uid，**查 DB** 確認該列存在且 `name` 一致後再 **Register** WebSocket。若列缺失或名稱不符，認證失敗（須修庫或重跑建表流程）。

## API 一覽

**共同 API**：連線後先 **auth/validate**。

| 路由          | packType | 方向            | 說明                                                                                                                                                                                                                     |
| ------------- | -------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| auth/validate | request  | Client → Server | **必填** `ValidateReq.device`（見上表）。`token` **僅對 `device=player` 有意義**：續玩 `uid=<n>`（n 須為 player 表列、且不可為 1～4）；首登 `register&name=<url-encoded>&age=<n>&sex=<n>`。固定終端 **`token` 可忽略**。 |
| auth/validate | response | Server → Client | ValidateResp { uid }。`player` 首登／新建列時 uid ≥ 5。                                                                                                                                                                  |

**玩家端 notify**：**notify/air_museum/player**，payload `PlayerInput`（ACTION_ENTRY、LEAVE、INPUT、SAVE_APPEARANCE 等）。uid 由 Server 依連線填入。

**投影端 notify**：**notify/air_museum/state**，僅連線 uid=1（主機）可送有效 `GameState`；Server 填入房內 uids 後廣播給其他房內成員。

**Server 推送**：notify **air_museum/player**（轉發給主機）、**air_museum/state**（廣播狀態）、**air_museum/error**、**air_museum/add_player**（payload `AddPlayerNotify`：對照 `player` 表整列含 `mission`、`game_score`、`landing_score`、`ranking`、`creattime` 轉 **Unix 秒** 等；現送 **playerRegisterScreen** 之 WS uid=2，例：`SAVE_APPEARANCE` 成功寫庫後）。**未認證**送 `air_museum/*` 時會依 gate 規則拒絕。

**約定細節**（仍以程式為準）：人數上限 **maxPlayers**、INPUT 是否僅房內、`SAVE_APPEARANCE` 對象等，可能隨產品調整。**本文件不重複固定「進房順序／房間與 ENTRY 的流程」**，避免與日後規則衝突時文件過時。

## 認證（Auth）提要

### 投影幕（gameScreen／projector）

`device = gameScreen`（或 `projector`）：`token` 可空。auth 時自 **player** 表讀取 **uid=1** 種子列並驗證 `name`，再 `SetHost`、`Add(uid)`（依目前實作），重複連線視為重連並可能清理房內其他連線（見程式）。

### kiosk（playerRegisterScreen／airplaneScreen／playerGameEndScreen）

`token` 可空。auth 時自 **player** 表讀取對應之 **種子列 uid（2～4）** 並驗證 `name`，通過後綁線；**不**呼叫 `CreatePlayer`。

### 玩家（player）

依 `token` 分支：**register** 建列並綁連線 ; **uid=**續連查 `player` 表 ; **空 token**新建匿名列。**拒絕** `token uid` 為 1～4（保留給固定終端）。

## notify／air_museum/state 與 air_museum/player

| 項目   | 說明                                                                             |
| ------ | -------------------------------------------------------------------------------- |
| state  | 主機送出 `GameState.state`；廣播的 `uids` 為當時房間實作的成員列表。             |
| player | ENTRY／LEAVE／INPUT／SAVE_APPEARANCE 等，由業務 Handler 決定是否在房／是否轉發。 |

## 斷線與連線清理

- 重複 **同一 uid** 登入：關閉舊連線並覆蓋連線映射。
- **主機**重連：`auth` 內對房間邏輯依現行程式（包含對其他連線發錯誤與移除房內成員）。
- **player**：斷線回調對房間的移除依 `cleanup.go`／遊戲階段。

---

## 未認證與錯誤

未 auth 發業務路由時依 gate／middleware 回錯。**auth** 錯誤（未知 device、`player` token 無效、`uid` 落在保留區等）回傳錯誤，Client 可依訊息重試。
